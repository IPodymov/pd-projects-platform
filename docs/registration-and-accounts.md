# Регистрация и управление учётными записями

## Регистрация

На странице входа есть ссылка «Зарегистрироваться» (`/register`). Пользователь вводит ФИО, email, пароль с повтором и, необязательно, дату рождения. Аккаунт создаётся после подтверждения шестизначного кода из письма. После подтверждения пользователь автоматически входит и открывает свой профиль.

Код действует 15 минут, повторная отправка доступна через минуту, максимум пять неверных попыток. Пароль проверяется стандартными валидаторами Django и хранится только в виде хеша. Пароль, код и права нельзя назначить через дополнительные поля запроса. Подтверждённая регистрация не даёт административных ролей, класса, курсов или проектов.

Зарегистрированный пользователь может принять существующее приглашение учреждения после входа. Самостоятельная регистрация не заменяет назначение сотрудника через приглашение.

API:

- `POST /api/v1/registration/request/`: `display_name`, `email`, `password`, необязательное `date_of_birth`; ответ 202 с `id` запроса.
- `POST /api/v1/registration/confirm/`: `id`, `code`; ответ содержит сессию и устанавливает session cookie.
- Перед обеими операциями клиент получает CSRF через `/api/v1/session/`. Обе операции защищены CSRF, включая анонимные запросы.

Письмо отправляется через существующий durable outbox и Celery. Payload содержит только UUID заявки. Код хранится зашифрованным, проверяется через HMAC. После подтверждения секреты заявки очищаются; истёкшие заявки очищает периодическая задача `accounts.tasks.expire_registrations`.

## Учётные записи администратора

Новый раздел «Учётные записи» в административной навигации (`/manage/users`): поиск по ФИО/email, пагинация, карточка пользователя, классы и история, курсы с прогрессом и проекты.

Администратор учреждения видит связанные с его учреждением аккаунты, включая историю членств, и может:

1. Добавить нового зарегистрированного пользователя по точному подтверждённому email в класс своего учреждения.
2. Редактировать ФИО и дату рождения доступного пользователя.
3. Назначить первый класс или перевести из выбранного текущего класса в другой класс того же учреждения.
4. Записать пользователя на опубликованный курс через его действующий класс.
5. Добавить пользователя в существующий открытый проект его класса либо создать новый проект и сразу добавить пользователя.

Сотрудник или ученик чужого учреждения не может быть найден через глобальный список и не назначается по email администратором другого учреждения. Подтверждённый аккаунт без прежних назначений можно добавить по email. После этого он появляется в списке учреждения.

Администратор платформы управляет всеми аккаунтами и дополнительно может отключать и включать обычные аккаунты. Учётные записи администраторов платформы отключать нельзя. Преподаватели, кураторы и студенты не имеют доступа к этому разделу/API. Email редактируется владельцем через существующее подтверждение новой почты; роли сотрудников назначаются существующими приглашениями и назначениями.

## Перевод и история

Перевод завершает старое членство, создаёт новое и переносит активные записи курсов в новый класс. Работы остаются в тех же записях курсов. Завершённые и отменённые записи курсов сохраняют прежний класс. Участие в прежних проектах сохраняется, автоматической смены класса проекта нет. Межучрежденческий перевод не поддерживается.

Существующее правило платформы сохраняется: повторное членство в том же классе и учебном году не создаётся. Для нового учебного года используется отдельный класс. При нескольких текущих членствах администратор выбирает, какое перевести.

Повторное добавление в существующий класс, курс или проект не создаёт дубликат. Если пользователя повторно добавляют в проект с другой ролью, его существующая роль сохраняется; изменение роли доступно через отдельный существующий интерфейс команды. Создание нового проекта является отдельной операцией.

Все изменения карточки требуют `If-Match` с её `updated_at`: без него 428, устаревшие данные — 409. Запись защищена транзакцией и блокировкой пользователя. Неудачное создание проекта с назначением участника откатывается полностью. Действия сохраняются в аудите без секретов.

API управления:

- `GET /api/v1/users/` и `GET /api/v1/users/:id/`.
- `PATCH /api/v1/users/:id/`: `display_name`, `date_of_birth`; `is_active` — только для администратора платформы.
- `POST /api/v1/users/add_student/`: `email`, `classroom`.
- `POST /api/v1/users/:id/set_class/`: `classroom`, при переводе `membership` текущего членства.
- `POST /api/v1/users/:id/add_course/`: `course`, `classroom`.
- `POST /api/v1/users/:id/add_project/`: `project`, необязательная начальная `role` (`member`/`leader`).
- `POST /api/v1/users/:id/create_project/`: `title`, `classroom`, необязательное `description`.

## Запуск и проверки

Применить миграцию `accounts/0006_registrationrequest_user_updated_at.py` командой `make migrate` при работающем локальном Compose. Для писем должны работать Mailpit/SMTP, Redis, worker и beat; после изменения Python-кода перезапустить worker и beat.

Проверки регистрации покрывают CSRF, реальную постановку/исполнение outbox и письмо в тестовом почтовом backend, хеширование, сессию, лимит попыток, повторную отправку и очистку секретов. Проверки администратора покрывают область доступа, запрет повышения привилегий, профиль и ревизии, классы, перенос активных курсов, идемпотентность, откат ошибочного создания проекта и полный сценарий регистрации → класса → курса → проекта → создания документа от лица нового пользователя.
