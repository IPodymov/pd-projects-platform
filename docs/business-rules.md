# Бизнес-правила и контракт операций

Этот документ задаёт поведение продукта, а не объявляет все пункты реализованными. Матрица в конце связывает правила с кодом и проверками. `/api/v1/` — новый контракт; `/api/` сохраняется как совместимый переходный маршрут. Роли складываются, полномочия всегда проверяются в области конкретного объекта. Данные пользователей и операционные события не входят в production seed.

## Учреждения и назначения — BR-01

Платформенный администратор создаёт учреждения. Администратор учреждения управляет своими годовыми классами и назначениями; куратор сопровождает назначенные учреждения; преподаватель видит назначенные классы; учащийся — своё членство и команды. Назначение преподавателя и членство учащегося независимы. Активное назначение может относиться к нескольким классам одной школы; разные школы требуют разных назначений. Учебный год не изменяет исторические результаты: создаётся новый класс и новое членство, прежнее завершается. Отключение назначения сохраняет историю, отзывает текущие права и фиксируется в аудите. Нельзя переместить класс, проект или назначение в другое учреждение через PATCH.

## Приглашения и импорт — BR-02

Статусы pending → accepted/revoked/expired; последние состояния терминальны. Перевыпуск создаёт новую строку и отзывает прежнюю. Ссылка и email-код должны соответствовать одному приглашению и живому сроку. Подтверждение ссылки без владения почтой запрещено. Существующий аккаунт должен войти и подтвердить привязанный адрес; пароль остаётся прежним. Принятие под блокировкой создаёт назначение/членство один раз. Импорт: preview → applied/expired, только автор и доступный класс; ошибки не применяются частично. Повторное применение возвращает отчёт без новых людей. Совпадающее ФИО не является ключом; конфликт имени и email требует решения сотрудника. Исправление email до регистрации отзывает все старые ссылки/коды; после регистрации только владелец проходит новый процесс подтверждения. XLSX содержит только действующие ссылки; значения экранируются от формул, экспорт приватный и аудитируемый. Письмо создаётся после успешного изменения данных и повторяется при временной ошибке доставки.

## Курсы и обучение — BR-03

Курс draft → published → archived. Опубликованный курс имеет хотя бы одно задание; архивный не принимает новые записи/работы. Управляют администратор/куратор учреждения, преподаватель оценивает назначенные классы. Запись active → completed/cancelled; completed вычисляется после принятия всех обязательных заданий. Отмена не удаляет результаты; повторная запись возобновляет ту же запись. Участник должен состоять в классе учреждения курса. Задания имеют срок, критерий и обязательность. Работа draft → submitted → revision/accepted; доработка создаёт новую отправку со ссылкой на предыдущую, не изменяя старый результат. Черновик не считается учебным действием; отправка считается. Просроченная отправка допустима и помечается поздней, поскольку педагогическая проверка важнее автоматического отказа. Прогресс — принятые обязательные задания / все обязательные задания × 100, при отсутствии заданий 0. Учащийся не задаёт результат и процент.

## Проекты — BR-04

Проект draft → active → submitted → revision/accepted → archived. Учитель класса задаёт этапы/критерии, состав и дедлайн; участник команды меняет описание и отправляет работу. Этап planned → active → submitted → revision/accepted. Принятие этапа требует принятия всех его заданий и проверяющего из области класса. Проект принимается только при принятых этапах/заданиях. В команде есть leader/member, но лидер не получает полномочия преподавателя. Работа относится к конкретной неизменяемой отправке и, при вложении, DocumentVersion того же проекта. После submitted текст этой отправки не редактируется. Проверяющий может оценить только submitted; две конкурентные проверки не перезаписывают друг друга. ReviewEvent хранит историю решения и замечания. Обязательное замечание для revision. Новая отправка не отменяет историю предыдущей. Общекомандный прогресс считается по заданиям, индивидуальная статистика отправок отдельно.

## Документы и Git — BR-05

Оригинал и цепочка версий неизменяемы. Создание версии блокирует документ, восстановление создаёт новый объект. 20 МБ файл, 50 МБ распакованный Office, UTF-8 текст, закрытый allowlist расширений; XML и архив недоверенные. Сравнение queued → processing → succeeded/failed, результат привязан к двум версиям одного документа. Повторный запрос того же сравнения не создаёт дубль. Diff содержит строки и диапазоны символов, DOCX-блоки/таблицы либо PPTX-слайды; не обещает визуальное сравнение оформления. Worker повторно проверяет текущий доступ инициатора.

GitHub и GitVerse используют разные адаптеры и заголовки. Токены только на сервере. Репозиторий принадлежит проекту, путь строго проверяется. Webhook проходит проверку подписи/секретного заголовка провайдера и сохраняется по delivery key; повтор не создаёт события. Событие ставит синхронизацию актуального состояния провайдера вместо слепого применения старого payload. PR open/closed/merged независим от учебного review pending/accepted/revision; review хранит head SHA. Новый head делает старую проверку stale, не стирает её. Проверяющий назначается только из преподавателей/кураторов проекта.

## Расписание — BR-06

scheduled → rescheduled/cancelled/completed; cancelled/completed терминальны. Администратор/куратор меняет события своей школы; преподаватель и учащийся читают свои занятия. Перенос сохраняет серию и отмечает исключение. Изменение серии по умолчанию не затрагивает исключения. Локальное время серии сохраняется в timezone, UTC используется для хранения. Новое время всей серии применяется как локальное календарное смещение от выбранного события, а не фиксированные UTC-секунды; DST проверяется. Начало < конец; online требует HTTPS URL, очно — место и комнату. Пересечения преподавателя, класса и помещения запрещены в транзакции. Изменение расписания создаёт аудит и уведомления; ссылки не выдаются публично. Посещаемость фиксирует преподаватель класса/куратор и только для участников занятия.

## Мастер-классы и партнёрства — BR-07

Партнёрство pending → active → ended, даты упорядочены; вуз и школа должны иметь правильные типы. Организатор управляет своим вузом, ведущий видит назначенное мероприятие. Workshop draft → published → cancelled/completed. Регистрация только в окне дат и доступной аудитории. all/partners/selected проверяются по действующим партнёрствам именно этого вуза. Индивидуальная и групповая запись имеют общий unique(workshop,user). Последние места блокируют Workshop; excess → waiting, отмена confirmed продвигает первого по времени. Ответственный школы может отменить своих групповых участников; организатор — любых в своём мероприятии. Отмена мероприятия отменяет все записи, не продвигает очередь и уведомляет участников. Факт посещения допускается только для confirmed после начала. Возрастные ограничения требуют даты рождения, сохранённой владельцем с подтверждением пароля (не документальная проверка возраста); отсутствие данных при ненулевом ограничении — понятная ошибка, а не молчаливый обход. Рассылки новых событий/открытия регистрации только подписавшимся уполномоченным сотрудникам, не всем ученикам.

## Публикации и конкурсы — BR-08

Публикация draft/published/archived, публикация требует контент и тему. Публично видны только опубликованные записи; управление — платформа. Конкурс опубликован и срок ещё не прошёл для новой заявки. Заявка draft → submitted → revision/accepted/rejected/cancelled; отправитель — участник проекта, проект/команда доступны ему. Проверяющий платформы решает заявку; замечание обязательно для revision/rejected. Повторная отправка только после revision, история переходов сохраняется. Заявка и подтверждение публикации для production — разные процессы. Данные заявок никогда не экспортируются в seed.

## CRM, аудит, уведомления — BR-09

Входы хранятся отдельными LoginEvent, а не выводятся из последнего входа. Период полуоткрытый [from,to), ISO с timezone, максимум 366 дней; отображение — выбранный timezone браузера, агрегация сравнивает UTC. Учебно активный — отправивший работу, загрузивший версию или изменивший проект в период; простой login и черновик не входят. Прогресс — принятые задания, не количество отправок. Просрочка — due_at < now без принятого задания. Все querysets ограничены разрешёнными классами. Нет показателя online без heartbeat.

Notification имеет тип, event key/target, получателя, read_at и статус доставки. Unique(event_key,recipient) ограничивает повторы. Outbox создаётся в одной транзакции с событием. Диспетчер забирает committed записи, retry/backoff и lease восстанавливают работу после падения. SMTP не даёт гарантии exactly-once при падении между send и commit: используем устойчивый Message-ID и явно документируем at-least-once. Пароли/токены/коды не попадают в аудит/логи; временные секреты в outbox зашифрованы и уничтожаются при завершении/истечении.

## API и интерфейс — BR-10

v1 использует пагинацию, разрешённые фильтры и стабильные ошибки {code,detail,fields,status}. 401/403 — авторизация/область, 404 — недоступный объект, 409 — конфликт/устаревшая форма, 400 — поля. Состояния меняют явные действия, не произвольный PATCH. Для изменяемых объектов If-Match содержит updated_at из прочитанного объекта; отсутствие на v1 значимой операции — 428. UI показывает ошибку полей/конфликт и сохраняет ввод, не объявляет успех до сервера, блокирует повторный submit, подтверждает отмену/отзыв и предупреждает о несохранённом вводе. Сгенерированный клиент обновляется вместе с OpenAPI. Старый /api/ поддерживается для существующих клиентов на время перехода.

## Production seed — BR-11

Только закрытые технические темы и явно утверждённые опубликованные недемонстрационные материалы. Никакие новые модели не добавляются автоматически. Stable keys, версия/checksum, замкнутые разрешённые зависимости, dry-run по умолчанию, транзакция, ручной конфликт блокирует импорт. Нет удалений, подключения export к production и startup/deploy auto-import. Процесс: локальная подготовка → export → validate/diff/утверждение → target dry-run → backup → явный apply.
