# Управляемый перенос данных

## Различия

| Механизм                  | Назначение                                                          | Запуск                                                                        |
| ------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Schema migration          | изменение таблиц/constraints, версии кода                           | manage.py makemigrations; migrate, API pre-deploy                             |
| Data migration            | детерминированное изменение уже существующих данных для новой схемы | makemigrations --empty <app>, затем RunPython/RunSQL; migrate                 |
| Development fixtures/demo | локальный пример сценария, тестовые пользователи и работы           | только явная demo_data, development; тестовые фабрики в изолированной test БД |
| Production seed           | отобранные согласованные справочники и утверждённые материалы       | export -> validate/diff -> target dry-run -> backup -> apply                  |

Data migration не является способом перенести локальных учеников или публикации в production. В этой итерации специальные data migrations не потребовались; миграции схемы созданы Django CLI. Demo data создаётся идемпотентной management command, а не startup hook.

## Allowlist формата 1

| Модель                   | Ключ | Поля                                                                              | Условие экспорта                                                                   |
| ------------------------ | ---- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| publications.topic       | code | title                                                                             | только engineering, robotics, research                                             |
| publications.publication | slug | title, body, topic, published, approved_for_production, is_demo                   | только при --include-approved-materials; published=true, approved=true, demo=false |
| publications.competition | slug | title, requirements, deadline, topic, published, approved_for_production, is_demo | то же                                                                              |

Три технических кода — согласованный набор в коде, расширение требует изменения allowlist и review. Произвольные Topic из локальной БД не экспортируются. Public material поля — plain text, авторы, local numeric IDs и произвольные FK отсутствуют.

Запрещены все остальные модели и все неизвестные поля. Нет Users, паролей, почт, токенов, sessions, персональных записей, реальных учреждений, классов, назначений, прогресса, проектов, документов, проверок, приглашений, партнёрств, расписания, посещаемости, активности и заявок. Связи закрыты: topic каждого материала обязан находиться внутри того же seed и соответствовать техническому набору; импорт не подтягивает связанные данные из локальной или production БД.

Checksum SHA-256 вычисляется по canonical JSON с format_version и records (без checksum). Это проверка целостности, **не цифровая подпись редактора**. Утверждение материалов и Git review остаются необходимы; редактор проверяет, что plain text не содержит случайных персональных данных или секретов. Автоматическая семантическая проверка содержимого не заявляется.

## Порядок

1. Локально подготовить технические данные и материалы. Для материала в Admin явно выставить published и approved_for_production, оставить is_demo=false.
2. Явно вызвать seed_export. По умолчанию — только технические справочники; материалы требуют флага. Экспорт имеет только локальные DB credentials, не обращается к production.
3. seed_validate, просмотр JSON и Git diff. Нечувствительные утверждённые файлы могут быть версионированы отдельно от development data.
4. В выбранном окружении целевого backend вызвать seed_import --dry-run. Это только чтение DB; никакие строки и SeedReceipt не сохраняются.
5. Сделать резервную копию и проверить возможность восстановления.
6. Только явным seed_import --apply применить одну транзакцию. Секреты целевой БД находятся в окружении процесса, не в seed/Git.

Повторный импорт не дублирует. Обновление допустимо только если текущее содержимое соответствует последнему SeedReceipt. Новая существующая запись без receipt с другим содержимым — конфликт. Совпадающая запись пропускается. При ошибке валидации, конфликте или save откатывается весь импорт. PostgreSQL advisory lock сериализует параллельные seed-imports. Удаление отсутствующих строк и принудительная перезапись не реализованы намеренно. Конфликт выводится как CommandError с natural keys, без подключения к другой среде.

Команды описаны в README. Ни обычный старт, ни deploy API/worker/beat seed не применяют. `make seed-plan`/`make seed-apply` адресуют только локальный Compose; для production нужно явно выбрать нужное окружение и выполнить команды там. Случайный перенос всей БД командой dumpdata не используется.
